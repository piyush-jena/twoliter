# Authenticated GPT systemd boot images

The experimental `systemd-boot-ab = true` image feature selects the dedicated Bottlerocket systemd loader for non-UKI disk images. It requires `uefi-secure-boot = true` and `in-place-updates = true`. It rejects UKI, EIF, standalone and encrypted-storage combinations. Existing variant defaults are unchanged. This path requires UEFI firmware; new images do not install GRUB BIOS boot code.

The loader uses the existing BOOT/ROOT/HASH bank layout and PRIVATE filesystem. Shim authenticates the systemd loader and ext4 driver. Each BOOT filesystem contains the signed kernel and a signed PE manifest whose `.brconf` section contains `BRBOOT1` plus NUL, the SHA-256 digest of the signed kernel bytes, and a NUL-terminated printable ASCII command-line template. The loader resolves exactly one `@ROOT@` and one `@HASH@` token against the selected bank. It authenticates and hashes the same buffered kernel bytes. Fixed flags and dm-verity parameters are covered by the manifest signature. Mutable `settings.boot.*` input remains a bootconfig-only LoadFile2 payload; executable initramfs prefixes are rejected.

Image generation signs the EFI loader and driver first and places the complete EFI filesystem image at `/usr/share/bottlerocket/bootloader/efi.img` in the root filesystem. Root verity therefore authenticates the staging payload. It then calculates root verity and signs the BOOT manifest. Repack re-signs the EFI staging image before rebuilding the root hash, then regenerates the signed manifest with the new kernel digest and verity table. This order avoids circular dependencies. Repack preserves the manifest's SBAT contents and checks the rebuilt section bytes.

Intermediate images retain a signed GRUB configuration on BOOT so an installed legacy loader can boot the new OS before an EFI transition. Installing an OS update alone does not switch an existing firmware loader. The matching core-kit supplies `signpost-bootloader.service`, which stages the retained backup EFI partition after the OS boot-success gate and arms a one-time `BootNext` trial. A further reboot through that entry is required before the OS acknowledges and promotes the loader. The original ESP and GPT geometry remain intact for recovery. Builder output alone is insufficient; deployments must include and qualify that installed transition service.

PCR prediction detects the dedicated loader and omits values that depend on bank selection, firmware driver authentication or legacy shim delegation. See the pcrsys README for the register list. Firmware qualification and real installed update/rollback tests remain necessary before changing default variants.
